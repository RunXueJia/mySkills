# 通用项目协作规范

> 适用于前后端分离、含数据库与异步任务的 Web 项目。实际项目可按技术栈替换目录名、命令和框架，但应保留分层、变更记录、配置安全和验证原则。

## 1. 项目结构

推荐按职责拆分目录，避免业务代码、接口代码、数据访问和页面代码混在一起。

```text
project/
  backend/                 后端服务
    app/
      main.py              应用入口
      api/                 API 路由
      services/            业务逻辑
      repositories/        数据访问
      models/              ORM/数据模型
      schemas/             请求与响应校验模型
      tasks/               后台任务/定时任务
      libs/                通用工具
    sql/
      database.sql         全量建表 SQL
      change.sql           增量变更 SQL
    docs/
      iterations/          重要迭代记录
    config.example.yaml    配置模板
    config.yaml            本地真实配置，禁止提交
  frontend/                前端项目
    src/
      api/                 请求封装
      components/          通用组件
      views/               页面
      stores/              状态管理
      router/              路由
  docs/                    跨端文档、产品说明、联调说明
```

如项目存在原始源码、历史版本或外部集成代码，应单独放置并标明是否允许修改，例如 `legacy/`、`third_party/`、`integrations/`。

## 2. 基本开发流程

- 修改前先确认需求影响范围：接口、数据库、前端页面、后台任务、配置、权限、日志和部署。
- 优先遵循现有代码风格，不为了小改动引入新的框架、目录或抽象。
- 新增功能按“接口 -> 业务逻辑 -> 数据访问 -> 模型/表结构 -> 前端接入”的顺序梳理。
- 修复问题时先定位原因，再改代码；不要只针对表象做硬编码绕过。
- 改动应尽量小而完整：同一需求涉及的接口、页面、SQL、文档和验证说明要同步处理。
- 不要随意改动历史源码、生成产物、构建产物或用户明确要求保持不变的页面结构。

## 3. 后端分层规范

后端推荐使用清晰的分层结构：

```text
endpoint/controller -> service -> repository/dao -> model
schema/dto 用于请求参数、响应结构和数据校验
```

各层职责：

- `endpoint/controller`：只处理路由、参数、权限、响应封装，不堆业务细节。
- `service`：承载业务流程、状态流转、跨表处理、外部服务调用编排。
- `repository/dao`：只处理数据库查询、写入和事务相关逻辑。
- `model`：定义数据库实体或领域模型，避免写复杂业务。
- `schema/dto`：定义输入输出结构，避免前端直接依赖数据库模型。

接口需要登录、权限或租户隔离时，应统一使用框架提供的依赖、装饰器或中间件，不要在每个接口里重复散写校验逻辑。

## 4. API 约定

项目应统一 API 前缀、版本和返回格式。

示例：

```text
/api/v1/resource
/admin-api/v1/resource
/account-api/v1/resource
```

统一返回结构示例：

```json
{
  "code": 200,
  "message": "成功",
  "data": {}
}
```

接口规范：

- 列表接口使用 `GET /resource/list` 或 `GET /resource`，并明确分页、筛选和排序参数。
- 详情接口使用 `GET /resource/{id}`。
- 新增接口使用 `POST /resource` 或 `POST /resource/create`。
- 更新接口使用 `PUT /resource/{id}` 或 `PUT /resource/update/{id}`。
- 删除接口优先使用逻辑删除，并明确是否允许物理删除。
- 前端请求路径应与后端统一前缀配合，避免同一项目同时出现多套 baseURL。
- 修改请求字段、响应字段、错误码或兼容行为时，必须同步更新前端调用和迭代记录。

## 5. 前端规范

前端目录按用途组织：

- `src/api/`：封装接口请求，不在页面中直接拼接大量请求细节。
- `src/components/`：通用组件，跨页面复用。
- `src/views/`：页面级组件，负责页面布局和业务状态组织。
- `src/stores/`：全局状态，例如当前用户、当前组织、当前选中资源。
- `src/router/`：路由配置和必要的路由守卫。

页面开发原则：

- 保持既有交互和视觉结构，除非需求明确要求重做。
- 页面数据必须来自当前上下文，例如 URL 参数、路由参数、store 或本地缓存，不得硬编码业务 ID。
- 空数据、加载中、失败、权限不足和处理中状态都要有明确处理。
- 轮询接口必须有停止条件，避免页面长期无意义请求。
- 前端展示字段应与后端 schema 对齐，不要依赖临时字段或默认假数据掩盖问题。
- 构建产物如 `dist/`、`.vite/`、`node_modules/` 不应提交。

## 6. 数据库与 SQL 规范

数据库变更必须可追溯。

- 全量建表 SQL 写入 `sql/database.sql`。
- 表结构调整、字段增删、索引变更、备注变更、初始化数据写入 `sql/change.sql`。
- 修改数据库字段时，模型、schema、repository、service、前端字段映射要同步检查。
- 表备注用于说明表级信息；字段备注只说明字段自身业务含义。
- 删除字段前先确认历史代码、后台任务、前端页面和数据迁移是否仍依赖该字段。
- 重要状态字段要明确枚举含义，例如 `-1失败 0待处理 1处理中 2完成`。

建表示例：

```sql
CREATE TABLE IF NOT EXISTS `example_table` (
  `id` INT NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `status` TINYINT NOT NULL DEFAULT 1 COMMENT '状态：0删除 1正常',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='业务说明:示例表;负责人:xxx;调用频率:实时';
```

## 7. 配置与密钥

- 真实配置文件必须加入 `.gitignore`，例如 `config.yaml`、`.env`。
- 仓库中保留 `config.example.yaml` 或 `.env.example`，说明必要配置项。
- 访问密钥、数据库密码、OSS/云服务密钥、模型 API Key 不得提交。
- 本地开发、测试、生产环境应使用不同配置，不要把生产配置复制到代码中。
- 配置变更影响服务启动、代理、端口、外部服务时，需要同步更新部署说明。

## 8. 文件上传与外部服务

- 上传接口只负责接收、校验、存储和返回文件信息；耗时解析建议交给后台任务。
- 文件名、对象存储 key、临时路径应使用安全字符，避免中文、空格和特殊符号导致签名或访问问题。
- 支持的文件类型、大小限制、存储位置和返回 JSON 结构必须明确。
- 调用外部服务时要记录必要日志，并处理超时、失败、重试和错误落库。
- 外部服务返回结构不稳定时，应做容错解析，但不能吞掉关键错误。

## 9. 后台任务与状态流转

后台任务应具备可恢复能力。

- 任务每次只领取明确状态的数据，例如 `status=1 and task_status=0`。
- 领取任务后先更新为“处理中”，避免重复执行。
- 每完成一个耗时子步骤就保存阶段结果，避免中断后从头重跑。
- 全部完成后更新为“完成”，失败后更新为“失败”并写入错误信息。
- 常驻循环任务应有合理 sleep 间隔，没数据时打印清晰日志。
- 任务依赖的配置、命令、工作目录和安装依赖应写入文档。

状态示例：

```text
-1 失败
0  待执行
1  执行中
2  执行完成
```

## 10. 日志与错误处理

- 接口错误要返回稳定结构，不把内部异常、密钥、完整 SQL 暴露给前端。
- 后台任务日志要能看出当前处理对象、当前步骤、成功或失败原因。
- 噪声日志应可通过配置关闭，关键业务日志不能被完全隐藏。
- 错误信息落库时保持简洁，必要时保留外部服务错误码和摘要。

## 11. 本地运行与端口

- 文档中明确后端启动命令、前端启动命令、后台任务命令。
- 前端代理路径必须与后端 API 前缀一致。
- 如果本地端口被占用，先确认占用进程是否属于当前项目；属于当前项目时优先复用，不属于时再换端口或询问处理。
- 生产环境反向代理要保留 API 前缀，避免路径被错误截断。

示例：

```powershell
cd backend
python -m app.main

cd frontend
npm run dev
```

## 12. 验证要求

不要为了很小的改动频繁跑完整构建。优先选择和改动范围匹配的检查：

- 后端小改动：语法检查、相关单元测试、相关接口冒烟测试。
- 前端小改动：相关组件页面预览、类型检查或局部测试。
- 数据库变更：确认 SQL、模型、schema、接口和页面字段同步。
- 任务脚本变更：至少验证一次无数据、成功处理和失败处理路径。
- 公共能力或跨模块变更：再考虑完整测试或完整构建。

验证命令示例：

```powershell
python -m py_compile path/to/changed_file.py
npm run lint
npm run test
npm run build
```

## 13. 重要迭代记录

满足任一条件时，应在 `docs/iterations/` 新增或更新迭代记录：

- 改接口请求、响应字段、错误码或兼容行为。
- 改数据库模型、迁移、配置、权限或状态流转。
- 改异步任务、扣费、日志、队列、外部服务调用或重试策略。
- 影响前端主要用户流程、后台管理行为或权限边界。
- 修复线上问题，且原因、影响或回滚方式值得追溯。
- 新增、删除或重构重要模块、第三方集成、provider 或 adaptor。

记录命名建议：

```text
docs/iterations/YYYY-MM-DD-short-topic.md
```

记录内容至少包含：

- 背景：为什么改。
- 变更内容：改了什么。
- 接口/兼容性影响：对调用方有什么影响。
- 数据/配置影响：是否需要迁移、初始化或配置调整。
- 验证：做过哪些检查。
- 回滚方式：出问题时如何恢复。

## 14. Git 与交付

- 不要提交真实配置、本地缓存、构建产物、日志和临时文件。
- 不要回滚他人或用户已有改动，除非得到明确要求。
- 提交前检查改动范围，确保没有无关文件混入。
- 最终说明应包含：改了哪些文件、关键行为变化、做过哪些验证、哪些验证未执行及原因。
- 如果项目有代码评审要求，优先说明风险、缺陷和缺失测试，再给变更摘要。

## 15. 可复制的 AGENTS.md 模板

可以把下面内容作为项目根目录 `AGENTS.md` 的起点，再按实际项目补充。

```markdown
# 项目协作说明

## 项目结构

- `backend/`：后端服务。
- `frontend/`：前端项目。
- `backend/sql/database.sql`：全量建表 SQL。
- `backend/sql/change.sql`：增量 SQL。
- `backend/config.yaml`：本地真实配置，禁止提交。

## 开发规范

- 后端按 `endpoint -> service -> repository -> model` 分层。
- schema/dto 用于请求参数和响应结构校验。
- 接口统一返回 `{ code, message, data }`。
- 前端请求统一使用项目约定的 API baseURL。
- 页面数据不得硬编码业务 ID，应来自路由、URL、store 或接口。
- 修改数据库字段时，SQL、模型、schema、接口和前端字段映射必须同步。
- 后台任务必须有明确状态流转，失败时写入错误信息。
- 真实配置、密钥、构建产物和本地缓存不得提交。

## 验证

- 小范围改动优先做局部检查，不频繁跑完整构建。
- 后端可运行相关文件语法检查或相关接口测试。
- 前端可运行相关页面预览、类型检查或局部测试。
- 数据库和接口变更必须同步检查调用方。

## 重要迭代记录

涉及接口、数据库、配置、权限、异步任务、外部服务、主要用户流程或线上问题修复时，在 `docs/iterations/` 记录背景、变更、影响、验证和回滚方式。
```
